<details>
<summary><b>🔍 How documind's corrective-RAG pipeline works</b></summary>

<br>

A plain RAG system answers confidently from bad context. This one grades its own retrieval and backs out when the context is weak.

```mermaid
flowchart LR
    Q([User Query]) --> R{Router}
    R -->|needs documents| HR[Hybrid Retrieval]
    R -->|general| SYN
    HR --> RRF[RRF Fusion]
    RRF --> RK[Reranker]
    RK --> G{Relevance Grader}
    G -->|context is good| SYN[Answer Synthesis]
    G -->|context is weak| WS[Web Search Fallback]
    WS --> SYN
    SYN --> HC{Hallucination Check}
    HC -->|grounded| A([Cited Answer])
    HC -->|not grounded| HR

    style Q fill:#F75C7E,stroke:#ffffff,color:#ffffff
    style A fill:#3FB950,stroke:#ffffff,color:#ffffff
    style G fill:#FBBF24,stroke:#333333,color:#333333
    style HC fill:#FBBF24,stroke:#333333,color:#333333
    style WS fill:#22D3EE,stroke:#333333,color:#333333
```

**The two decision points are the whole idea.** The *relevance grader* catches weak retrieval before it reaches the model, and the *hallucination check* catches ungrounded output before it reaches the user — looping back rather than shipping a confident guess.

Stack: LangGraph orchestration · FastAPI · PostgreSQL + pgvector · typed React/Vite frontend with a live agent-status timeline.

</details>

<details>
<summary><b>🔍 How seat-wave prevents double-booked seats</b></summary>

<br>

Two people click the same seat in the same millisecond. Exactly one may win.

```mermaid
sequenceDiagram
    participant A as User A
    participant B as User B
    participant API as .NET API
    participant DB as PostgreSQL

    A->>API: reserve seat 14C
    B->>API: reserve seat 14C
    API->>DB: BEGIN SERIALIZABLE for A
    API->>DB: BEGIN SERIALIZABLE for B
    DB-->>API: A reads seat, xmin is 42
    DB-->>API: B reads seat, xmin is 42
    API->>DB: A writes if xmin still 42
    DB-->>API: A commits, xmin now 43
    API->>DB: B writes if xmin still 42
    DB-->>API: B rejected, xmin changed
    API-->>A: confirmed
    API-->>B: seat taken, pick another
    API->>A: SignalR broadcast, seat map updated
    API->>B: SignalR broadcast, seat map updated
```

`SERIALIZABLE` isolation plus PostgreSQL's `xmin` system column gives optimistic concurrency without a distributed lock. Losers get a clean rejection, and every connected client's seat map updates live over SignalR.

</details>

<details>
<summary><b>🔍 How a compiler fits together front-to-back (SLangJava)</b></summary>

<br>

```mermaid
flowchart TD
    SRC([slang source file]) --> LEX[ANTLR Lexer]
    LEX --> PARSE[ANTLR Parser]
    PARSE --> AST[Abstract Syntax Tree]
    AST --> TC{Type Checker}
    TC -->|type error| ERR([Diagnostics])
    TC -->|well typed| INTERP[Tree-Walking Interpreter]
    TC -->|well typed| CODEGEN[Java Codegen Backend]
    INTERP --> RES([Immediate Result])
    CODEGEN --> JAVA([Generated .java])

    style SRC fill:#F75C7E,stroke:#ffffff,color:#ffffff
    style TC fill:#FBBF24,stroke:#333333,color:#333333
    style ERR fill:#EF4444,stroke:#ffffff,color:#ffffff
    style RES fill:#3FB950,stroke:#ffffff,color:#ffffff
    style JAVA fill:#3FB950,stroke:#ffffff,color:#ffffff
```

One front end, two back ends: the same type-checked AST either runs immediately through the interpreter or lowers to Java source. The 174 tests exist because a port is only correct if it disagrees with the original *nowhere*.

</details>
